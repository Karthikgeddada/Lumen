# Lumen Python Pipelines

Open-source Python parsing pipelines for Lumen. One **pipeline module per
workspace nav item**, built individually:

| Module | Pipeline | Status |
| --- | --- | --- |
| 1. Document Library | **Parsing engine** — pdfplumber (text + font-size heading detection + tables), python-docx (true body order), openpyxl (values **and** formulas with cell refs), pandas (CSV) | ✅ built · runs in-process in the Node worker (2026-11-26) |
| 2. Data Extraction | Field-extraction engine on top of #1 | planned |
| 3. Analytics | pandas stats + chart-ready aggregates | planned |
| 4. AI Assistant | Local RAG (sentence-transformers + FAISS) | planned |
| 5. Questionnaires | Scoring / consistency engine | planned |

All dependencies are permissive open-source licenses (BSD/MIT/Apache). No
cloud accounts, no API keys, no paid services.

## How it runs (one service, zero configuration)

The parsing logic lives in `parsers.py` (pure functions; heavy libraries
import lazily, and only the ones the file type needs). Two entry points,
same contract:

- **`parse_once.py` — the production path.** The Node worker spawns it per
  document (`python3 parse_once.py <file> <name>`); it prints the parse
  JSON to stdout and exits 0, or prints a reason to stderr with a nonzero
  exit — the worker then falls back to its JS parsers and logs the reason,
  so uploads never fail because of Python. On Render, `lumen-api`'s build
  installs `requirements.txt` into a venv and `LUMEN_PYTHON_BIN` points
  the worker at it. Locally, a plain `python3` with the deps installed
  works; with no deps installed you get a logged JS fallback (nothing
  breaks).
- **`main.py` — an optional local HTTP harness** (FastAPI) with the exact
  same contract, for interactive debugging.

Optional escape hatches (see ENVIRONMENT.md): `LUMEN_PYTHON_PARSERS=false`
disables the Python parsers; `PARSE_SERVICE_URL` + `PIPELINES_TOKEN`
switch the worker to a remote sidecar if the Python workload is ever
split onto its own service again.

## Run locally

```bash
cd backend/python-pipelines
pip install -r requirements.txt

# the way the worker runs it (no server at all):
python3 parse_once.py /path/to/some.pdf some.pdf

# or the optional HTTP harness for debugging:
uvicorn main:app --port 8100
curl --data-binary @some.pdf -H "Content-Type: application/octet-stream" \
     "localhost:8100/parse?name=some.pdf"
```

## Deploy (Render)

Nothing to deploy — there is no separate pipelines service anymore. The
`lumen-api` build (render.yaml) installs `requirements.txt` into a venv
(`/opt/py`) and sets `LUMEN_PYTHON_BIN`, so the worker finds the Python
parsers in the same service. No `PARSE_SERVICE_URL`, no token. If the
venv can't be built, the deploy fails loudly at build time — never a
silent parse downgrade.

## Contract

Both entry points emit the exact JSON shape the Node pipeline consumes
(`pageCount`, `ocrRequired`, `sections[]`, `tables[]`):

- `parse_once.py` prints it to stdout (exit 0; a nonzero exit means a
  parse failure, with the reason on stderr).
- `POST /parse?name=<filename>` (HTTP harness) returns it as JSON, with
  the file as the **raw request body** (`application/octet-stream` — no
  multipart library needed).

PDF table attribution (verified against a financial-statement fixture,
2026-11-26): each table gets a title from its own single-cell title row if
it has one ("Balance Sheets (In thousands)"), else from the nearest text
line **above** the table — never a heading from below it — and table
content is kept out of `sections` so it is never double-reported (it is
already chunked as table rows by the Node pipeline).

Caveat (verified): formula cells keep their provenance (`ref` + `f`), and
the computed value `v` comes from the cache the *saving application*
wrote. Excel/LibreOffice files carry it; files generated by openpyxl
itself do not (openpyxl never computes formulas — same limitation as the
previous JS parser).
